# Design Explanation

## 1. How the solution is designed

```
Parent text
   |
   v
service.handle()  -- validate (empty / too long)
   |
   v
rag.retrieve()              <- reference notes (glossary, valid site values)
   |
   v
interpreter.interpret()     <- Groq (strict JSON Schema)
   |  SearchCriteria (validated by Pydantic)
   v
clarify? --yes--> ask one question, no search
   |no
   v
rag.normalize_criteria()    <- snap location/division to the site's exact values
   |
   v
eschool_client.search()     <- builds URL, GET, parses HTML
   |  list[School]
   v
matcher.explain()           <- plain code, no AI
   |
   v
AssistantResponse (ok | needs_clarification | no_results | error)
```

Each layer has one job and is replaceable. The AI is used only where language
understanding is needed. Everything else is ordinary, testable code.

The browser UI is served by FastAPI from `app/static/` and submits JSON to the
existing same-origin `POST /search` route. It renders all four backend states:
successful results, clarification, no matches, and service errors. Keeping the UI
and API on one origin avoids a separate CORS configuration.

## 2. How a request becomes search criteria

The model is required to return strict JSON conforming to a schema generated from the
`SearchCriteria` Pydantic model. The reply is then validated again in code. The backend uses
Groq's OpenAI-compatible API and reads `GROQ_API_KEY` from the server-side `.env`; the key is
never sent to the browser. The system prompt instructs the model to fill a field only when the
parent stated it, to convert fee shorthand to UGX integers, to put non-filterable wishes in
`unsupported`, and to treat the parent's text as data rather than instructions.

Every field defaults to `None`, so "not specified" is never confused with a preference.
`SearchCriteria.specified()` returns only what the parent actually said.

### Retrieval-augmented grounding

Parents write "S1", "800k", "Nakawa" or "has vacancies". A small knowledge base
(`knowledge/`) holds reference material for exactly those terms plus the option values of
eSchool's own form. Relevant entries are retrieved per request and given to the model as
background notes, and the model is told they never add requirements. The knowledge base contains
no schools, in line with the brief. After interpretation, plain code maps the model's location, division and supported
category filters onto the site's exact option values, and leaves ambiguous values untouched.

## 3. How the application interacts with eSchool

`app/eschool_client.py` builds the same query-string format as the example URL
(`location`, `county`, `min_fees`, `max_fees`, `gender`) and maps other observed public form
filters to their current field names (`q`, `levels[]`, `accomadation`, `admission_status`,
`curriculums[]`, `facilities[]`, and `religions[]`). It sends one GET with a timeout and an
identifying User-Agent, and parses the public `article.card` listings with BeautifulSoup.
The current public empty-state message is treated as a valid zero-results response.
It does not use any private API and does not crawl.

The search supports boarding, level and admission-status filters, but the result card doesn't
show all these details. Admission class is not a filter and is checked against the parsed card
text where possible. Results remain the site's search results; the assistant does not claim that
unsupported filters narrowed them. If a card does not contain requested information, the
school is shown with that requirement marked as unconfirmed.

The county/area dropdown is populated dynamically and is empty in a static page
inspection. The prototype preserves a parent's county wording (including the task's
example value) instead of guessing a value from an incomplete option list.

## 4. Why this AI integration and technical approach

- **Strict JSON-schema output** gives structured criteria instead of parsing free text, and
  Pydantic validation catches malformed or out-of-range values.
- **AI only for interpretation.** Explanations are generated by `matcher.py` from fields that
  exist on the page, so the model cannot invent school details or claim a match the data does
  not support, which the brief explicitly forbids.
- **Python + FastAPI** gives a small API and CLI quickly, with typed models shared across layers.
- **Dependency injection** (`handle(..., interpret_fn, search_fn)`) lets tests run without an API
  key or network.

## 5. Ambiguity, missing information and failures

| Situation | Behaviour |
|---|---|
| Empty or over-long input | Rejected with a clear message before any AI call |
| Vague request (nothing searchable) | `needs_clarification` with one question; no search runs |
| Contradictory fees (min > max) | Pydantic validation error -> reported as an AI interpretation error |
| Criterion the site cannot filter | Disclosed in the response; checked against card text or shown as unconfirmed |
| Soft wishes ("strong sports") | Listed under "Not searchable"; never silently dropped |
| School data missing (e.g. no fees) | Shown as "not listed"; never counted as a match |
| No schools returned | `no_results` with suggestions to widen the search |
| eSchool down, timeout or HTTP error | `error` response; the interpreted criteria are still returned |
| Page structure not recognised | `error` ("Unexpected response format") instead of a false empty result |
| Knowledge base missing or corrupt | Retrieval returns nothing; interpretation continues without notes |
| AI call fails, no structured output, invalid output | `error` with the reason (for example an invalid model name) |

## 6. What I would improve with more time

- Refresh the option snapshot from the live form regularly and verify selectors against saved
  real result pages.
- Follow pagination and cache results briefly to be gentle on the site.
- Multi-turn conversation so a clarification answer refines the previous criteria.
- An evaluation set of 30+ realistic parent requests with expected criteria, run against the
  interpreter to measure accuracy and prompt changes.
- Result ranking by how many requirements are confirmed.
- Retry with backoff for transient site errors, plus rate limiting on the API.
- Run a few live, recorded integration tests against saved real pages in CI.
